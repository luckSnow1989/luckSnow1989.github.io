# 6.最佳实践

## 技术类工作难题
关于高可用、安全、扩展性和稳定性的工作，无法法进行量化，这些工作做得越早、越细，越难被证明，这也是行业里最经典的难题。如何解决这一问题？

### 1.案例
1. 成果的“隐性”与“反事实”特性：
   - 隐性：一个稳定的系统，用户和业务方感知到的就是“一切正常”。这种“无感知”恰恰是高可用工作的成功，但也使其价值变得“隐形”。
   - 反事实：你无法向老板展示“如果我们不做这些工作，会发生什么灾难性后果”。你不能真的把系统搞垮来证明自己的价值。你只能通过理论分析和模拟演练来推断可能的风险。
2. 投入的“前置性”与“持续性”：
   - 前置性：架构设计、技术选型、代码规范、基础设施建设等工作都需要在项目早期投入大量资源，但其收益可能在数月甚至数年后才显现。
   - 持续性：稳定性不是一劳永逸的，需要持续的监控、优化、重构和演练。这种持续性的投入容易被视为“日常开销”，而不是能直接产生业务价值的“投资”。
3. 价值衡量标准的缺失或错位：
   - 公司通常更关注直接的业务指标，如用户数、订单量、营收、增长率等。技术团队的贡献往往需要通过这些业务指标来间接体现。
   - 当业务快速增长时，人们倾向于将成功归功于产品、市场和销售，而忽略了稳定可靠的技术平台是这一切的基石。

### 2.解决方案

如何解决这一“吊诡”的问题？ 

解决这个问题的核心思路是：将隐性价值显性化，将技术成果业务化，将长期收益阶段化。

重点是要改变思维方式：从被动的“技术保障者”转变为主动的“业务赋能者”。你不是在“花费”公司的资源，而是在为公司的“数字资产”进行保值和增值。

#### 2.1.建立量化的技术指标体系
建立量化的技术指标体系（将隐性价值显性化） 。虽然直接量化“避免了多少次故障”很困难，但我们可以建立一套间接但有效的技术指标来衡量高可用、稳定性和扩展性的工作成效。
- 高可用 & 稳定性指标：
    - 核心指标：
        - 服务可用性 (Service Availability)：如 `(总时间 - 不可用时间) / 总时间`，目标通常是 99.9%、99.99% 等。
        - 平均无故障时间 (MTBF - Mean Time Between Failures)：衡量系统稳定性的重要指标。
        - 平均恢复时间 (MTTR - Mean Time To Recovery)：衡量故障处理效率。
        - 错误率 (Error Rate)：如 HTTP 5xx、4xx 错误占比。
    - 辅助指标：
        - 变更失败率 (Change Failure Rate)：衡量部署、发布过程的稳定性。
        - 服务依赖健康度：下游依赖服务的可用性对本服务的影响。
        - 资源使用率：CPU、内存、磁盘、网络等的使用率和饱和度，是容量规划和潜在瓶颈的预警信号。
        - 慢查询比例、接口响应时间 (P95, P99)：反映系统性能和用户体验。
- 扩展性指标：
    - 水平扩展能力：系统能否通过增加实例数量线性提升处理能力（可通过压测验证）。
    - 垂直扩展能力：单实例能否通过提升硬件配置提升性能。
    - 弹性伸缩效率：根据负载自动扩缩容的速度和准确性。
    - 架构解耦程度：可以通过“修改某一功能点涉及的代码范围”、“服务间接口依赖复杂度”等间接衡量。微服务架构的设计是否合理，服务边界是否清晰。
    - 数据库扩展性：分库分表、读写分离、NoSQL 等技术的应用成熟度。

行动建议：
- 选择与业务目标强相关的 3-5 个核心指标进行重点监控和汇报。
- 为这些指标设定明确的 SLA (Service Level Agreement) 和目标值。
- 定期（如每周、每月）生成技术健康度报告，展示这些指标的变化趋势。

#### 2.2.将技术成果与业务价值挂钩
将技术成果与业务价值挂钩（将技术成果业务化） 这是最关键的一步。你需要向管理层清晰地阐述，你所做的技术工作是如何直接或间接地推动业务增长、降低成本或提升用户体验的。
- 可用性 -> 业务价值：
    - “我们通过架构优化和容灾建设，将系统可用性从 99.9% 提升到 99.99%，这意味着每年减少了约 8.8 小时的不可用时间。按我们日均交易额计算，这直接避免了约 XX 万元的潜在损失，并保护了品牌声誉，减少了用户流失。”
    - “通过引入熔断、降级机制，在下游支付系统偶尔不稳定时，我们的核心下单流程仍能正常运转，保证了交易的连续性。”
- 稳定性 -> 业务价值：
    - “通过持续的性能优化和代码重构，我们将核心接口的 P99 响应时间从 500ms 降低到 200ms，用户下单转化率提升了 X%。”
    - “建立了完善的监控和告警体系，使我们能够在故障影响用户之前就发现并解决问题，大幅提升了用户满意度。”
- 扩展性 -> 业务价值：
    - “由于我们早期采用了微服务和容器化架构，在最近一次大促活动中，我们仅用了 XX 小时就完成了计算资源的 3 倍扩容，平稳支撑了日均 10 倍的流量峰值，保障了大促目标的顺利达成。如果是传统架构，这几乎是不可能完成的任务，或者需要数倍的成本。”
    - “清晰的服务边界和 API 设计，使得新业务模块的开发周期缩短了 X 周，加快了产品上市时间。”

行动建议：
- 在做任何技术决策时，都要思考其背后的业务驱动力和价值。
- 在汇报技术工作时，永远先讲业务影响，再讲技术实现。用业务语言翻译技术成果。
- 主动参与业务规划，提前预判业务增长对技术架构的挑战，并制定应对方案。

#### 2.3.进行有策略的“压力测试”和“故障演练”
进行有策略的“压力测试”和“故障演练”（将长期收益阶段化、可视化）。通过主动制造一些“可控的混乱”，可以非常直观地展示系统的韧性和你之前工作的价值。
- 混沌工程 (Chaos Engineering)：
    - 定期进行故障注入测试，如随机杀死一个服务实例、断开某个网络、模拟数据库慢查询等。
    - 记录故障发生后系统的表现（如是否自动恢复、影响范围、恢复时间）。
    - 将演练结果和改进措施向管理层汇报，展示系统的健壮性以及团队应对突发故障的能力。这比任何空洞的“我们做了高可用设计”都更有说服力。
- 性能压测与容量规划：
    - 定期对核心业务链路进行性能压测，找出性能瓶颈。
    - 根据压测结果和业务增长预测，制定容量规划方案，并提前进行扩容或架构优化。
    - 向管理层展示“我们的系统目前能支撑多少用户/订单，未来业务增长到 X 倍时，我们需要如何调整”，体现你的前瞻性和规划能力。

行动建议：
- 将混沌演练和性能压测纳入团队的常态化工作。
- 邀请业务和产品同事观摩关键的演练，让他们直观感受技术的稳定性价值。

#### 2.4.重视文档、复盘和知识沉淀
- 架构决策记录 (ADRs - Architecture Decision Records)：
    - 对于每一个重要的架构决策，都记录下来：背景（Context）、决策（Decision）、后果（Consequences）。
    - 这不仅有助于团队内部的知识传承，也能在未来向新的管理层或审计人员清晰地解释“为什么我们当初要这么设计”，证明决策的合理性和前瞻性。
- 故障复盘 (Post-mortems)：
    - 对于每一次线上故障（无论大小），都进行严肃、公正的复盘。
    - 分析故障根因、暴露的问题、改进措施。
    - 复盘报告是展示团队学习能力和持续改进文化的重要材料。即使是做得好的预防工作，也可以在复盘中提及“由于我们之前做了XX措施，这次故障的影响被控制在了XX范围”。

### 3.最佳实践

每天默默巡检，全年基本无问题，领导觉得你无作为；啥也不管，出了上线问题积极参与，领导觉得你能力很棒。

善战者无赫赫之功。所以线上应该出问题，但是都在自己的掌握之中。

## 高可用

高可用的目的是确保系统在遇到故障时能够快速恢复并继续运行，也就是保障系统的稳定性。
但是随着软件系统的不断的升级迭代，并且在降本增效的背景下，系统的高可用也面对着结构性的挑战。

高可用的挑战：
1. 熵增。赶工、堆需求、技术债累积、新技术不断加入，都在让系统变得更复杂。理论上通过规范和流程能改善，但现实中业务压力通常远大于质量压力，技术团队很难真正阻断系统滑向混乱。
2. 墨菲定律。只要系统在运行，意外就是必然：机房会坏，链路会断，软件和系统都有 bug。就算做了多活，真正需要切换时也可能失败。高可用是一场永远无法完全取胜的竞赛，只能尽可能延缓系统走向失控。

难题：
1. 很少有人主动去做。因为那些把隐患提前消灭的工作，往往看不见、量化不了
2. 系统一旦撑不住，重构、多活、混合云这些工程就会立刻成为重点。你一年修一堆细碎问题，年底材料并不好看，而隔壁团队虽然出过P0，却因大刀阔斧做架构升级，轻松拿到亮眼结果。

公司层面也面临同样矛盾：平时的投入看起来琐碎；真正出事故，又觉得当初投入不够。于是形成普遍循环：系统退化 → 重大事故 → 大规模治理 → 阶段稳定 → 再次退化。

解决方案：
1. 把高可用视为持续工程。 系统健康像身体健康，需要常态维护，而不是一次性升级。给团队留出质量时间，比突击式治理更可靠。
2. 接受高可用是慢变量。 隐患处理不会立刻带来收益，但能减少灾难级事故，也能让系统不至于一路滑向深渊。
3. 坚持体检。一年小复盘，两年大盘点，即便无法避免事故，也能把12小时的损失降成2小时，这对业务影响是本质差异。

高可用的难点不在技术，在于组织能否给系统留出生长和修复的空间。

## 稳定性

什么是稳定性：系统持续稳定可靠的提供服务，核心关注系统“不出问题” 或者 “出问题后多快能恢复”

稳定性指标有哪些？
1. 可用性 (Availability)： (总时间 - 不可用时间) / 总时间 * 100%。是结果性指标。
2. 成功率 (Success Rate)： 请求处理成功的比例 (HTTP 200/2xx 比例)。是过程性指标。
3. 延迟/耗时 (Latency)： 请求处理的耗时 (P50, P90, P95, P99, P999)。关注长尾延迟。
4. 流量 (Traffic/Throughput)： 系统处理的请求量/数据量。
5. 其他重要指标： 错误率、饱和度（资源利用率）、MTTR (平均恢复时间)、MTBF (平均无故障时间)。

保证系统稳定性的措施有哪些？

防御：避免发生 或者 可以忽略问题。分层防御体系建设，主要分为静态 与 运行态 两中。
- 静态防御：
  1. 架构设计。通过设计评审提前发现问题。
  2. 代码优化。迭代中CodeView，定期的清理技术债，完善文档，避免“黑箱操作”。
  3. 自动化测试。单元测试、集成测试、UI 测试等。
  4. 自动化部署 + 配置管理（减少人工失误，如用 Jenkins、配置中心统一管理）；
- 运行态防御：
  1. 接入层：限流（计数器/时间窗口/漏桶/令牌桶）、WAF(web应用防护)、负载均衡、异地容灾（SLB调度），基于IP的流量控制
  2. 应用层：降级+熔断、异步解耦（削峰填谷）、并行执行、无状态服务、服务拆分、请求超时、数据库长连接控制（会话时长、自动检测）等。
  3. 存储层：分库分表、读写分离、缓存分级。
  4. 运维层：架构层容量规划、弹性扩缩容、强弱依赖解耦、混沌工程、灰度发布等。

问题定位于恢复：应急预案、全链路监控/告警、链路追踪、自动化运维等。

保证系统稳定性的常见案例？
1. 秒杀：流量分层（CDN动静分离、限流降级熔断）、异步请求、预扣库存等。
2. 异地多活：核心问题:数据冲突，解决方案：表分库分表（或分区），网关层面就近调用，ETL数据同步。
3. JVM稳定性：OOM日志+MAT分析、G1/ZGC大内存低延迟+NewRatio+并发回收线程数、线程池拒绝策略。

复杂问题排查思路：现象定位->变更回溯->链路追踪->日志挖掘->复现验真->修复。

如何设计高可用系统：逐层回答
1. 基础设施：同region多AZ，
2. 应用层：无状态+集群
3. 数据层：主备（主从）切换

告警的核心原则是什么？如何避免“告警疲劳”？
核心原则： 准确、及时、可操作、有优先级。 告警信息要清晰说明 What (发生了什么), Where (发生在哪里), When (什么时候), Severity (严重程度), 以及初步的 Why (可能原因) 和 How (如何应对)。

避免告警疲劳：
- 分级告警： 设置不同级别（P0/P1/P2/P3），不同级别通知不同人员/渠道。
- 收敛/聚合： 将相关告警合并，避免轰炸。
- 抑制： 在已知大规模故障期间，抑制次要告警。
- 静默： 计划维护期间静默预期告警。
- 关联分析： 将告警与拓扑、变更、指标关联，减少噪音。
- 定期评审优化： 去除无效告警，调整阈值，确保告警有意义。
- 自动化： 自动化响应常见低级告警。

## 扩展性

如何设计可扩展性的系统架构？

什么是可插拔设计？
可插拔接口的核心是 “接口约定 + 动态加载”，通过解耦核心框架与功能模块，实现系统的灵活扩展。Java 常用 SPI 机制，依赖配置文件实现服务发现。实际开发中，需根据语言特性选择合适的实现方式，
核心目标是最小化扩展成本，最大化系统灵活性。
在Java应用设计中，以SPI为例，可插拔设计需要实现以下原则（开闭原则，对扩展开发，对修改关闭）
1. 接口抽象。统一接口或者抽象类，规定插件必须实现接口的方案，明确使用的规范。
2. 插件管理。核心框架需要提供插件注册、管理、调度等功能。
3. 动态扩展。组件可以单独开发编译等，通过配置文件或者扫描机制等被核心框架可以发现组件。
4. 隔离性。组件故障，不会影响核心框架使用，核心框架升级不强制要求组件修改源码，只要接口兼容即可。

可插拔接口的典型应用场景
1. 日志框架：Slf4j 定义日志接口，插件可替换为 Logback、Log4j 等实现；
2. 数据库驱动：JDBC 定义接口，不同数据库（MySQL、Oracle）通过 SPI 提供驱动实现；
3. IDE 插件：如 IDEA 的插件市场，用户可按需安装插件扩展功能；
4. 工作流引擎：如 Activiti 允许通过插件扩展节点类型或审批逻辑；

什么是插件化设计？
是可插拔设计的一种实际落地方式。
插件化设计的目的：核心功能不变，通过插件扩展功能。（通常实现方案：后端完整的，前端控制插件按照）
原则：“核心标准化+边缘定制化”
目的：提升系统的扩展性、实现项目交付效率提升，并提高系统的稳定性。
分层处理：
1. 核心层：封装通用功能（用户管理、权限控制、专利查询等核心业务等），定义统一 API 接口；
   实现方式：提供中心层SDK帮助调用方简化调用，统一功能入口，封装底层逻辑，提升开发效率。
2. 插件层：将定制需求（如跨部门审批、自定义报表）开发为独立插件，通过插件市场供租户自主启用，设置 CPU / 内存配额防止资源滥用；
3. 配置层：通过特性开关（Feature Flag）满足轻量级需求（如流程节点显示差异），配合零代码设计器支持字段扩展、界面布局调整。

## 重构

什么是系统重构？为什么要重构？
- 系统重构：就是在不改变系统对外提供功能的前提下，实现内部的优化和改造的过程。
- 核心：帮助系统架构演进，而非推倒重来。提升系统的扩展性、稳定性、以及代码的可维护性。
- 如何判断需要重构了：1、系统事故频发；2、业务转型需求；3、技术整合（多个系统业务合并）；4、代码质量低下，难以维护；5、架构设计落后，无法适用业务发展；6、性能存在瓶颈。
- 原则：以业务价值为导向，平衡系统稳定与架构演进，既不能畏惧分险而放任系统腐烂，也不能追求完美而激进重构。

如何重构？重构前先带着问题思考：
- 为什么重构？（明确目标，如提升性能、优化架构、降低维护成本）
- 重构什么？（识别核心痛点，如高耦合模块、性能瓶颈代码）
- 如何衡量成功？（定义可量化的指标，如代码行数减少、测试覆盖率提升、响应时间缩短）

引入概念：C4模型，是一种用于分层的软件系统架构模型。通过上下文、容器、组件、代码。
C4 模型将复杂的重构工程拆解为可理解、可执行的具体步骤，帮助团队在 “变化” 中保持对架构的掌控力，最终实现系统的平滑演进。

作为架构师：应该先区分是“架构设计缺陷”“资源配置不足”还是“业务逻辑冗余”，而非直接调参优化，确保解决方案直击本质。

重构策略：
1. 渐进式重构（Strangler Pattern）：通过“小步快跑、持续验证”的方式，逐步使用新功能替换旧功能。
2. 大爆炸式重构（Big Bang）：重新构建一个新的系统，新系统完全替换旧系统。

重构过程常见的技术困难？
1. 老版本兼容性。数据结构、接口查询条件、尤其是隐形契约（双方约定的字段规则）等。需要时间梳理。
2. 数据迁移。一致性问题和效率，例如大表迁移效率（选择合适的工具），数据库双写数据一致性（ETL同步或定时数据对账），历史脏数据处理（表结构、字段类型、约束条件等等）。
3. 灰度发布，新老版本共存。使用冗余部署、集成同一个系统等不同的方案，已经如何控制各自的流量。
4. 测试覆盖，重构中最怕的就是回归测试时遗漏场景，导致测试成本很高。没啥好办法，只能小步快走，后续补齐单元测试、集成测试等。
5. 上下游系统。找到所有的上下游系统，梳理调用链路，重构上线后方便故障定位。


重构过程与需求迭代发生冲突如何解决？
1. 时间盒：将重构穿插到需求迭代中，避免被业务时间完全积压。
2. 需求分级：明确重构和需求的优先级，合理安排时间。
3. 建立沟通机制：告知业务方重构带来的好的影响，争取时间资源。

领域驱动设计（DDD）如何指导系统重构？
1. 事件风暴（Event Storming）：通过工作坊梳理业务流程，识别核心域（如订单域、库存域）和支撑域（如支付网关、物流对接）。
2. 限界上下文划分：按业务边界定义微服务（如将 “用户注册” 与 “权限管理” 划分为不同上下文）。
3. 聚合根与实体设计：确保每个聚合根（如Order）有独立的生命周期管理，避免跨聚合的直接数据修改。
4. 防腐层构建：在新旧系统间添加适配器（如将遗留数据库查询转换为领域模型），防止外部系统逻辑污染核心域。

重构案例：
1. 旅游行业重构：通过 DDD 将酒店信息整合为统一模型（消除不同代理商的命名差异），并拆分为 “酒店基础服务” 与 “价格策略服务”，提升业务响应速度。
2. 金融风控系统：将关联分析逻辑从 Elasticsearch 迁移到图数据库（Nebula），利用图结构天然支持复杂关系查询，提升实时性与存储效率。
